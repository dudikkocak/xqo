# xqo reference

xqo is a headquarters of agents: agents are organised into **departments**, each with a head, contact rules, its own workspace and notes board, and an optional budget.

Claude-powered agents that message each other directly, broadcast skill lookups to hand tasks over, share a notes board, run their code in a sandbox, use MCP tools, and save every fenced code block as a timestamped artifact. A local dashboard shows the live message flow, flags you when an agent needs you, and lets you browse, diff and roll back artifacts. Design: [MASTERPLAN.md](MASTERPLAN.md).

## Quick start

### uv
```bash
uv venv && source .venv/bin/activate   # always create the virtual environment with uv
uv pip install .               # or: uv pip install ".[mcp]" for local MCP servers
uv pip install ".[sdk]"        # optional: Claude Agent SDK backend (default when installed; signs in with your `claude` login or the key)
export ANTHROPIC_API_KEY=sk-ant-...        # or `ant auth login`; PowerShell: $env:ANTHROPIC_API_KEY="sk-ant-..."
xqo init              # writes agents.json + departments/ to edit (optional; defaults are built in)
xqo serve             # open http://127.0.0.1:8000
xqo run "Write a CSV parser with tests"   # one task on the CLI (answers attention prompts in the terminal)
xqo run "Match this mockup" --attach ui.png --attach spec.pdf
xqo cancel <task_id>  # stop a running task (on the server)
xqo delete <task_id> [--permanent]   # to the trash; xqo restore <task_id> brings it back
xqo archive <task_id>  # hide a finished task from the task list (xqo unarchive brings it back)
xqo schedule add "Nightly check" "Build and test, report failures" --cron "0 2 * * 1-5" --tz Europe/Berlin
xqo schedule list     # also: pause | resume | run | rm | runs <schedule_id>
xqo --mock serve      # offline demo with a scripted model, no key needed
xqo --departments engineering,research serve   # load only some departments ("none" = HQ only)
```
`python -m xqo …` works too. `--data-dir` (or `XQO_DATA`) sets where `artifacts/` and `logs/` go; `--config` (or `XQO_CONFIG`) picks the roster. **One file for everything**: `xqo hq.json [command]` uses that file as the config, and its `"server"` block (`host`, `port`, `data_dir`, `departments`, `mock`, `url`) replaces the command-line options. Flags and environment variables still win. Size limits (workspace text files, image / PDF / text attachments) are set in its top-level `"limits"` block. See [SETUP.md](SETUP.md#one-master-config-file-per-instance).

### Docker
```bash
docker compose up --build      # dashboard on http://127.0.0.1:8000, data in ./data
# or
docker build -t xqo . && docker run -p 127.0.0.1:8000:8000 -e ANTHROPIC_API_KEY -v "$PWD/data:/data" xqo
```
Put your own `agents.json` in `./data` to override the built-in roster. Inside the container the sandbox uses the `local` backend (the container is the isolation boundary).

Try the demos in mock mode: a prompt containing **"confirm"** makes the planner ask you a question; **"run tests"** makes the tester run code.

## Departments
- **Config**: one JSON file per department in `departments/` next to `agents.json` (or `--departments-dir`, `XQO_DEPARTMENTS_DIR`; the packaged examples are used when there is no folder). Each file sets `name`, `description`, `head`, `agents` (same fields as in agents.json), `contacts`, and optionally `budget`, `sandbox` and `mcp_servers`. Agents listed in `agents.json` itself form **headquarters (HQ)**; shared defaults (model, effort, sandbox, git) stay there. Agent names are unique across departments. The examples: `engineering` (eng_lead; coder, reviewer, tester), `marketing` (mkt_lead; writer), `research` (research_lead; analyst), with `planner` at HQ.
- **Heads**: a head receives work from outside its department, assigns it to its members with `handover_task`, checks the results, publishes what others need, and reports back.
- **Two-level broadcast**: `handover_task` first looks for the skill inside the sender's own department. If nobody offers, it asks the heads of the departments the sender may contact. A head offers when one of its members has the skill, and the winning head assigns the work inside its department. Target one department with `department="marketing"` or a skill like `@marketing copywriting`.
- **Judged fit** (optional, `"offer_judge"` in agents.json, off by default): offers are ranked by the free skill match first (exact 2, partial 1, then least busy). A model is asked only when that cannot decide well: **two or more offers tie** on the best skill score (only the tied ones are judged), or **the task is large** (`large_chars`, default 2000) and there are two or more offers (all are judged, up to `max_candidates`). Each candidate gets one small call returning `{"fit": 0-1, "reason": "..."}`; ties are then broken by fit (rounded to 0.1, so near-equal fits fall back to load), and on large tasks fit comes before the skill label. Task text is treated as data. A timeout, refusal, bad reply or missing client leaves the free ranking in place; a handover never fails because of the judge. The decision is an `offer` event (`meta.judge`: mode, per-candidate fit, reason, cached, winner), each call an `llm` event, and its tokens count against the department budget. **Caching**: the instructions are the system prompt and the task text is the first, cache-marked block, so all candidates share a prompt-cache prefix (with `warm_cache` the first call goes alone so the rest read it; providers only cache prefixes above their minimum length, so small tasks will not cache); fit scores are also kept in memory for `cache_ttl` seconds under (candidate config hash, judge model, prompt version, skill + task hash), so retries, forks, schedules and feed rules do not pay twice, and editing an agent invalidates its entries. Load is never cached. `GET /api/config` shows `offer_judge` (calls, cache hits, failures, tokens). Settings: `enabled`, `model` (a small model such as `claude-haiku-5-5` is enough), `provider`, `effort`, `large_chars`, `max_candidates` (4), `timeout` (20 s), `max_tokens` (300), `cache_ttl` (3600; 0 = off), `cache_size` (512), `warm_cache` (true), `max_task_chars` (6000). `XQO_OFFER_JUDGE=0` turns it off for one run. Changes need a restart (department reload does not re-read it). Not active in `--mock` mode.
- **Permissions**: `contacts` lists the departments a department may reach (`"*"` = all; HQ is always reachable and can reach everyone). `ask_agent` works inside a department; across departments it must go to the head. A department's `sandbox` settings and `mcp_servers` apply only to its own members.
- **Shared resources**: each department has its own notes board and workspace per task (`artifacts/<task>.<department>/`, with its own git history). Agents use them with `scope="department"` on `note`, `read_notes`, `list_files`, `read_file`, `write_file`, `patch_file` and `run_code`, and share files with `publish_files` (a `publish` version in the task workspace). Fenced code blocks still land in the shared task workspace. Zips include department workspaces under `departments/`.
- **Budgets**: `"budget": {"max_tokens": 3000000, "max_cost_usd": 15}` caps what a department spends on one task tree. When it's reached you're flagged (`extend` adds another budget, default `stop`), and a stop ends only that department's work. Costs use built-in per-model rates (Claude Opus 5.5: $4 / $20 per million input/output tokens); override them with `"pricing": {"<model>": {"input": …, "output": …, "cache_read": …, "cache_write": …}}` in agents.json.
- **Dashboard**: the graph draws a box per department with thicker lines between departments, the agents panel is grouped by department with tokens, cost and a budget bar for the selected task, the Live viewer can filter by department, and the notes board can switch to a department's board.
- **Loading**: `--departments a,b` (or `XQO_DEPARTMENTS`) picks which files to load. **↻ reload** on the dashboard, or `POST /api/departments/reload`, re-reads the files without a restart. Work already running finishes on the old agents. A reload with an error changes nothing. It also re-reads agents.json and the skill packs, and starts, restarts or stops local stdio MCP servers to match.

## Skills, tools and MCP per agent
MCP servers, **skill packs** (`skills/<name>/SKILL.md`, loaded by agents with `load_skill`) and a **tool policy** (`allow` / `deny` patterns) are granted like `model`: the agent's `mcp` / `skill_packs` / `tools`, else its department's `default_*`, else `default_*` in agents.json. A list replaces what it inherits, `"+name"` adds to it, and `{"server": ["get_*"]}` filters one server's tools for one agent. New tools come as MCP servers. Details and examples: **[OPERATIONS.md](OPERATIONS.md)**.

## Backups and upgrades
`xqo backup` (full, `--scope state` or `--scope config`; channel sign-in tokens and secrets are never included), `backup verify|restore`, `xqo check` (load the config with a new version before switching), `xqo drain` (stop new work, wait for running tasks), versioned data with migrations at start-up, `/api/health`, and version-tagged Docker images for rollback. Step-by-step upgrade path: **[OPERATIONS.md](OPERATIONS.md)**.

## Local feeds
Agents can watch **this machine and its jobs**: CPU, memory, disk, processes, systemd services, files, log files, the journal, Docker events, and events that cron jobs, scripts, git hooks and CI send (`xqo feed emit backup --status $?`, or GitHub / GitLab webhooks). Rules in `"feed_rules"` (`when`, `for`, `clear`, `severity`, cooldowns, caps, quiet hours) pick what matters, without any model call, and **log** it, raise a **notice**, collect a **digest** task per hour, or **wake** an agent; later events of the same incident go to the open task. Each agent's `"feeds"` access is `none` (default), `read`, `wake` or `act`. Woken tasks run in **report** mode (read-only tools) unless the rule says **act**, which adds the rule's tools and fixed `feed_actions` commands, each approved by you first. Event text reaches agents as untrusted data. Setup and every setting: **[FEEDS.md](FEEDS.md)**.

## Messaging channels
Agents can watch and answer **Telegram, WhatsApp, Instagram, X, Threads, Gmail and SMS (Twilio)** messages. Each agent's `"channels"` setting is `none` (the default), `operator` or `responder`, for all channels or per channel. **Operators** (the channel's `operators` list) drive the HQ from their phone: a message starts a task or asks the running one, `/steer`, `/status`, `/cancel` and buttons for the agents' questions, and the results come back to the chat. Anyone else reaches **responder** agents: their text arrives framed as untrusted data, the task can only reply (no code, files, delegation or MCP unless the agent's `channel_tools` allows it), and each reply waits for an operator's **send** (or an edited text) unless `approve_replies` is `false`. Rate limits, allow/block lists, platform reply windows and a secret check on outgoing replies are built in. Telegram, X, Gmail and SMS poll, so they need no public URL; an email only counts as an operator's when it passes DMARC or DKIM. Webhooks are signature-checked and can get their own port (`"webhook": {"port": 8443}`) so the dashboard stays private. `xqo channels` shows the status. Setup per platform, costs and every setting: **[CHANNELS.md](CHANNELS.md)**.

## Several HQs and peering
Run several isolated HQs (one process or container each, with its own data dir, port, departments, budgets and keys), and optionally let them exchange **messages, workspace files (text or binary) and attachments**, only with the peers each one lists. On one machine they share an exchange folder; across machines they use a separate peer listener (`"listen"`) with one bearer token per pair. An incoming message starts a task with the receiver's own agents, and with `want_reply` its final answer comes back into the sender's task. HQ agents and department heads get `list_peers` / `send_to_peer`. With the Claude Agent SDK backend they reach Claude Code through the in-process `xqo` MCP server like the other xqo tools. The dashboard's **⇆ peers** button and `xqo peers` show the links and the recent messages. All variants, step by step: **[SETUP.md](SETUP.md)**. Three instances with Compose: [`deploy/multi/`](deploy/multi/docker-compose.yml).

## Agents from agency-agents
Import ready-made specialists from [agency-agents](https://github.com/msitarzewski/agency-agents) (MIT, ~280 agent prompts in divisions such as engineering, testing, security, marketing) and keep them current:
```bash
xqo agency list --division engineering            # browse (* = imported)
xqo agency add engineering/engineering-code-reviewer.md --skills "code review,security"
xqo agency add testing                            # a whole division (paths, globs or division names)
xqo agency update --dry-run                       # what changed upstream for your agents
xqo agency update                                 # move to the newest commit and regenerate
xqo agency remove code_reviewer                   # by path, glob or agent name
```
- **Where they go**: an existing department file gets them next to its own members, a new one (default: the agent's division) is created with a generated head; `--department hq` puts them in agents.json. Each imported agent gets the upstream prompt as `system` plus a short adapter paragraph about the xqo tools, its emoji as avatar and its own name as the default skill. **↻ reload** on the dashboard (or `--reload`) picks up department files; agents.json (HQ) changes need a restart.
- **Your changes** live in `agency.json` next to agents.json: per upstream path any agent field (`skills`, `name`, `model`, `effort`, `can_run_code`, `write_paths`, `mcp`, …, `department`), plus `ref` (branch/tag/commit to follow, default `main`), `adapter` (`null` = built-in, `""` = none) and `departments` (settings for generated departments: `description`, `contacts`, `budget`, `head`, `default_model`, …). Run `xqo agency sync` after editing it. Generated agents carry `"_agency"` and are rewritten on every sync; hand-written agents are never touched, so edit agency.json, not the generated entries.
- **Pinned**: `agency.lock.json` records the upstream commit and a hash of each imported file. `add`, `remove` and `sync` stay on that commit; only `update` (or `update --ref <tag|sha>`) moves it. The update report lists **changed** (with a +/- line count), **renamed** (followed automatically when the content is identical), **missing** (deleted upstream: the last imported version is kept until `--prune`) and how many agents are new upstream (`list --new`).
- **Safe**: names must stay unique (set `"name"` in agency.json on a clash), and the result is loaded once before it counts: any error puts every file back. `--source <checkout>` reads a local clone instead of fetching (git, else a GitHub download).
- **Scheduled check**: `xqo agency update --check` writes nothing and exits 1 when one of your agents changed upstream, e.g. for a weekly CI job that opens a PR with the result of `update`.
- **Licence**: upstream's MIT licence is saved as `AGENCY_AGENTS_LICENSE` next to agents.json on every sync; keep it with the copied prompts.

## How it works
- **Agents** are defined in `agents.json`: `name`, `skills`, `system`, optional `model`, `effort`, `max_turns`, `can_run_code`, `mcp` (server names or `"all"`), `write_paths` (glob patterns of the workspace files the agent may write, e.g. `["plans/**", "*.md"]` for the planner: `write_file`, `patch_file` and fenced blocks outside them are refused with a reminder to hand the change to engineering; unset = any file). **Model per agent**: each agent can set its own `"model"` (e.g. `"claude-haiku-5-5"` for a cheap helper) and `"effort"` (`low`…`max`); unset ones fall back → the department file's `default_model` / `default_effort` → `default_model` / `default_effort` in agents.json → `XQO_MODEL` / built-in `claude-opus-5-5`, effort `medium`. Bad values stop startup with a clear error. The Agents panel shows each agent's model, a *default* / *dept default* chip when it isn't set on the agent, its effort, and the model that actually answered when a fallback served the last call. Defaults: server-side refusal fallback on (`XQO_FALLBACKS=0` disables).
- **Claude Agent SDK backend** (always installed in xqo-lite): when the `claude-agent-sdk` package is installed, `claude-sdk` is the default provider for every agent and each task runs in Claude Code. It signs in with `ANTHROPIC_API_KEY` or, without a key, the Claude Code login on the machine (`claude`, then `/login`; or `CLAUDE_CODE_OAUTH_TOKEN`). Agents also get Claude Code's own tools, set per agent with `"sdk_tools"` (default `["Read", "Grep", "Glob", "Edit", "Write", "Bash"]`; `"default_sdk_tools"` in a department file or agents.json; `[]` for none). Hooks keep them safe and visible: reads and writes stay inside the task workspace and follow `write_paths`; every Edit/Write is saved as a workspace version (history, diff, git commit, artifact event) like `write_file`; **Bash never runs on the host**: each command runs in the xqo sandbox (the department's, if it has one) on a copy of the workspace, only for agents with `can_run_code` (others get no Bash), with the usual run logs and test verdicts. Department members keep the `scope="department"` file tools and run_code for the department workspace. Tokens and cost from Claude Code count against department budgets, and a run stops before its next tool when the budget runs out. The xqo tools (handover_task, ask_agent, ask_user, reply_user, publish_files, notes, local and remote MCP servers) are served to Claude Code in-process, chat messages reach the agent between tool calls, fenced blocks are still saved, and `model`, `effort`, `max_turns` and `max_tokens` apply. Claude Code compacts its own history, so `compaction` and the max_tokens continue prompt are API-path features. Attachments are not sent as content to Claude Code agents: the task prompt and chat messages list their paths, and the hooks let Read, Grep and Glob open the task's attachments folder (read-only). Each Claude Code session's usage and cost (from its result messages: tokens, cache reads and writes, turns, duration, cost in USD per model) is stored on the task, logged as an `llm` event, kept in the task's `done` event (so it survives a restart) and shown as a badge in the task tree, with the sub-tree total on parent tasks. To stay on the API set `"default_provider": "anthropic"` in agents.json or a department (or `XQO_PROVIDER=anthropic`), or `"provider": "anthropic"` on one agent. When the SDK was only picked because it is installed and Claude Code can't start, the agent falls back to the Anthropic API (shown as provider source `fallback`); an agent that names `claude-sdk` explicitly fails with a sign-in hint instead. Docker: `docker build --build-arg EXTRAS=mcp,sdk …`.
- **Provider per agent**: optional `"provider"` on an agent: `claude-sdk` (default when installed, above), `anthropic` (default otherwise), `openai`, `ollama`, a name from `"providers"` in agents.json, or any OpenAI-compatible base URL (`"http://gpu:8000/v1"` for vLLM, LM Studio, LiteLLM…). Unset falls back to the department's `default_provider` (department file), then `default_provider` in agents.json, then `XQO_PROVIDER`, then `claude-sdk` when installed, else Anthropic. Keys come only from environment variables: each provider names one with `"api_key_env"` (presets: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`; Ollama needs none; an agent can set its own `api_key_env`). A plaintext `"api_key"` in the config is refused at startup. Example: `"providers": {"local": {"base_url": "http://localhost:8001/v1", "api_key_env": "LOCAL_LLM_KEY"}}`, then `{"name": "helper", "provider": "local", "model": "qwen3-coder"}`. Optional per-provider settings: `headers`, `timeout`, `extra_body`, `max_tokens_param`, `reasoning_effort`. OpenAI-compatible agents use the same tools (files, patches, run_code, delegation, chat replies, local MCP servers), attachments (images; text files inline; PDFs only on Anthropic), artifact extraction and usage tracking; failed calls are retried, then you are asked to retry. Remote MCP connector servers and the refusal fallback are Anthropic-only and are skipped for them. The Agents panel shows a provider chip (hover: where it was set, base URL, whether its key variable is set; red when missing); `/api/config` lists providers in use without keys.
- **Avatars**: optional `"avatar"` on an agent (and `"user_avatar"` in agents.json for the user node): an image file (png, jpg, gif, webp or svg up to 2 MB, path relative to the file that names it: agents.json or the department file), an http(s) image URL (loaded by the browser), or an emoji / up to 4 letters. It fills the agent's node on the graph, with the name moved below it, and shows next to the name in the Agents panel. Files are served at `/api/avatars/<name>` (sandboxed, no local paths sent to the browser); a missing or unsupported file stops startup with a clear error. **Drop-in folder**: an agent without `"avatar"` gets `avatars/<agent id>.<png|jpg|jpeg|webp|gif|svg>` when that file exists next to `agents.json`, and the user node gets `avatars/user.<ext>`; an explicit `avatar` always wins. `"avatars_dir"` (top level of agents.json) moves the folder, `false` turns it off. Only that folder is read, only plain files that live in it (no links out), up to 2 MB; anything else is ignored. Read at startup and by **↻ reload**, so adding an image needs no restart. Backups include the images in use.
- **Nicknames**: optional `"nickname"` on an agent (agents.json or a department file) and `"user_nickname"` at the top level of agents.json for the **user node** (whose id is always `user`). One line, at most 40 characters; a bad value stops startup with a clear error. It is a **display name only**: the dashboard (graph node label, Agents panel, entry/fork selectors, message flow, task tree, attention cards and notifications) and the office (name tags, side panel) show it, with the real id as a tooltip, while events, tools, `@agent` targeting, the CLI and the API keep using the id (`name`). `/api/agents` has `nickname` per agent and `/api/config` has `nickname` for the user. Avatars and nicknames combine: `"user_avatar": "🧑", "user_nickname": "Alex"`. **Addressing**: people can use the id or the nickname (case-insensitive, optional `@`) for the task entry agent (`POST /api/tasks`, fork, `xqo run --agent`) and for Ask / Steer targets; it is resolved to the id before anything is stored. Agent-to-agent tools (`ask_agent`, `handover_task`) take ids only. Nicknames must be unique (case-insensitive, user node included) and may not equal another agent's id, a department name, `hq`, `user` or `all`; a clash stops startup. The 2D and 3D office name tags show the nickname, and the office side panel titles the agent by its nickname with the id below it and its avatar left of the close button; the planners world shows `<hq>/<nickname>` (the id when the remote HQ has none, or runs an older version that does not send nicknames).
- **Graph layout**: the picker in the Flow graph header switches between **By department** (the default: a box per department), **Ring**, **Grid** or **Star** (the user in the middle); the flat layouts list agents in department order. Each browser remembers its choice; `"graph_layout": "departments" | "ring" | "grid" | "star"` in agents.json sets the default (an unknown value stops startup). Node order follows the config files.
- **History trimming (token saving)**: before each model call, tool traffic older than the last 2 tool exchanges is cut down to a short stub: test-run output keeps its first lines plus where the full log is saved, file reads say to `read_file` again, and file contents sent with `write_file` / `patch_file` say how many characters were sent. The task prompt, the agent's own text, chat messages and errors are kept. It runs in batches (only when ≥ 20,000 characters can be saved) so the prompt cache stays valid between batches. Settings: `"compaction": {"enabled", "keep_turns", "min_chars", "batch_chars"}` in agents.json; `XQO_COMPACT=0` turns it off. Each trim is an `llm` event, and the Agents panel shows the tokens trimmed so far.
- **Output limit (max_tokens)**: each call may write up to `max_tokens` output tokens (thinking included). Set it per agent (`"max_tokens"`), with `default_max_tokens` in agents.json (also per department file) and `XQO_MAX_TOKENS` as fallbacks; default 32000. Anthropic calls are streamed, so large limits work and long replies don't time out. For local OpenAI-compatible servers, set a value their model supports. A reply cut off at the limit is not the end: the agent is asked to continue exactly where it stopped (up to 2 times, then you are asked: continue / stop), the parts are joined, and files are extracted only from the finished reply. If it stays unfinished, an open code block is kept as a snippet and never written to the workspace. Agents are told to write long files with `write_file`, one file per call. The Agents panel shows how many replies were cut off; the model tooltip shows the limit.
- **No limits for an hour**: the *No limits* checkbox in the header turns off `max_turns`, `max_tokens`, the per-task time limit (`XQO_TASK_TIMEOUT`) and department budgets for every agent and task, running ones included, for one hour (output limit raised to `XQO_UNLIMITED_MAX_TOKENS`, default 128000). Ticking it again (or ↻ 1h) restarts the hour; unticking restores the limits at once; after the hour they come back by themselves. It is server state (`GET` / `POST /api/limits` with `{"enabled": true|false}`), so every browser sees the same countdown, and it survives a restart. Open time-limit and budget questions are answered *extend* when you tick it; when the hour ends, every task gets a fresh time period and a fresh department budget counted from where it stands, so nothing stops the moment the override ends. Scheduled runs keep their own `max_cost_usd`.
- **Attention alerts**: anything that needs you keeps the agent blinking until it is dealt with (its node in the flow graph, its badge and its desk monitor in the 2D and 3D office: red for a question or an error, amber for an auto-answered question, green for a finished task): an open question until you answer it, and a finished root task, an error or a question that was auto-answered until you dismiss it in *Needs your attention* (or the office panel's *To check*). Alerts are server state (`GET /api/alerts`, `POST /api/alerts/ack` with `{"ids"|"agent"|"root_id"}`), shared by every tab and kept across restarts; deleting, archiving or reopening a task clears its alerts. Sub-tasks don't alert when they finish, and unattended scheduled runs alert on errors only.
- **Submit feedback**: after *Submit*, *Ask* or *Steer* in the dashboard, the user node flashes until an agent responds on that task (its first reply, thinking step or acknowledgement).
- **Agent reports**: every agent's final answer is saved as a Markdown report, and agents can write more along the way with the `report` tool. Reports go to the artifact history as `<task>/<agent>/reports/<agent>_<time>_<title>.md`; a failed or cancelled task gets a short report (what happened, files touched). Double-click an agent in the office to see its last 10 reports under *Submit* and preview them (`GET /api/agents/<name>/reports`, `GET /api/reports/<path>`). Claude Code sessions take the limits when they start: one already running that reaches `max_turns` is told to continue while the hour lasts.
- **Agent tools**
  - `ask_agent(agent, message, title)`: direct message, waits for the reply.
  - `handover_task(skill, task, title)`: broadcasts "who has skill X?", collects offers (exact skill match beats partial, then least busy), hands the task to the winner and returns its result.
  - Both take an optional `files` list of shared-workspace paths. They are sent as references (path and size), not content: the receiver reads them with `read_file` or Read when it needs them, and agents are told never to paste file contents into messages. A message with an unfilled template slot (a `{content}` or `<your code>` line, `{code}` in prose, `[paste the file here]`) is refused with a tool error so the sender retries with the real content. Code inside fenced blocks is not checked.
  - `ask_user(question, reason, options, default)`: flags you on the dashboard and waits (see Attention).
  - `note(key, value)` / `read_notes()`: the shared notes board.
  - `list_files`, `read_file`, `write_file`, `patch_file`: the task workspace.
  - `move_file(src, dst)`: move or rename a workspace file, committed as one git rename. Agents use it instead of `git mv` (commands run on a copy of the workspace without `.git`, so a shell move would be lost). `write_paths` applies to both paths; an existing `dst` is refused.
  - `delete_path(path)`: delete a workspace file or a whole folder (e.g. a leftover `node_modules`), committed as one change. Agents use it instead of `rm`, which in a command only changes the run's copy. Read-only files are deleted too; `.git` and paths outside the workspace are refused; `write_paths` applies. Dependency and cache folders (`node_modules/`, `.venv/`, `venv/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`) stay on disk but are kept out of workspace commits (`.git/info/exclude`); run copies skip the caches but keep `node_modules`, since runs are offline.
  - `run_code(command)`: only for agents with `can_run_code` (the `tester`).
  - `list_agents()`, plus any MCP tools the agent is allowed to use.
- **Task names**: `task_<YYMMDDhhmm> : <title>` (local time; `-2`, `-3`… within the same minute). The root title is written by the model (falls back to the prompt's first line); sub-task titles come from the delegating agent. Folders and URLs use the ID; `artifacts/<task>/task.json` stores the full name and prompt.
- **Attention**: a task pauses with status `needs_attention` when an agent calls `ask_user`, or automatically when
  a task hits its time limit (`extend`/`stop`, default stop), API retries run out (`retry`/`stop`, default retry),
  no agent offers on a handover (pick an agent or `skip`), or patches still fail after their retries (guidance or `ignore`).
  If you don't answer within `attention_timeout` (agents.json, default **180 s**; `XQO_ATTENTION_TIMEOUT` overrides), the default answer is auto-confirmed. Time spent waiting on you doesn't count toward the task's time limit. Requests are logged as `attention_requested` / `attention_resolved` events and survive restarts.
- **Shared notes board**: one per task tree (`artifacts/<task>/memory.json`). Agents write facts and decisions with `note`; the current board is included when any agent starts a sub-task. You can add notes from the dashboard.
- **Sandboxed execution**: `run_code` copies the task workspace to a temp dir and runs the command there; changes are discarded. `sandbox.backend` in agents.json: `auto` (Docker if its daemon answers, else local), `docker` (`--network none`, memory/CPU/pid limits, image `astral/uv:python3.12-bookworm-slim` by default, which has uv), `local` (subprocess with a timeout and minimal env; **not** a security boundary), or `off`. `XQO_SANDBOX` overrides. Each run is saved as a `run` artifact. Run copies go to `sandbox.run_dir` (`XQO_RUN_DIR` overrides); by default the system temp dir on the local backend and `~/.cache/xqo/runs` with Docker, because Docker Desktop shares the home folder but not `/tmp` (copies older than a day are swept at startup). If Docker answers `mounts denied`, the run result names the path and the fix: share it (or a parent) in Docker Desktop → Settings → Resources → File Sharing, or point `run_dir` at a shared folder. The task venv (`artifacts/<task>/.venv-docker`) is mounted too, so keep the data dir under a shared folder as well. Python projects run in a **per-task virtual environment**, always created and filled with [uv](https://docs.astral.sh/uv/) (never `python -m venv` or pip): on the local backend `artifacts/<task>/.venv` (or `artifacts/<task>.<dept>/.venv` for a department workspace; outside the workspace so it is never zipped or committed), with Docker `artifacts/<task>/.venv-docker`, built inside the image with its uv (mounted at `/venv`; the image must have uv). Docker installs dependencies in a setup container with network access (`sandbox.setup_network`, default `true`); the run itself stays offline. Without uv the code runs without a venv and the result says so. The xqo Docker image includes uv. Dependencies from `pyproject.toml` (incl. optional deps and dependency groups) and `requirements*.txt` are installed on first run and again only when those files change; pytest is added when the project has tests. `uv run` / `uv sync` use the same env. Agent `pip install …` / `python -m pip …` commands run as `uv pip install …` on the task venv (the result shows `[ran as: …]`), the venv gets `pip`/`pip3` shims that call uv pip on it, and xqo's own venv is removed from PATH, so packages never go into xqo's environment. Settings: `sandbox.venv` (default `true`), `python` (e.g. `"3.12"`), `setup_timeout`, `setup_network`; `venv_tool` is always `uv` (older values still load); a department's `sandbox` block can override them.
- **Other languages (local and Docker backends)**: Node (incl. Nuxt and Next), Go, Rust and .NET projects get their own setup next to Python's venv. The workspace is split into **components**: folders with `package.json`, `go.mod`, `Cargo.toml` or `*.sln`/`*.csproj` (up to 3 levels deep, never inside `node_modules`, `vendor`, `target`, `bin`/`obj` …; npm/pnpm/yarn workspaces, `go.work`, a cargo `[workspace]` or a `.sln` own the folders below them). So a Go API with a Nuxt app in `web/`, or a FastAPI app with a Next front end, is two components, each installed separately and both available in every run. Before a run, each component whose manifest or lockfile changed is set up, otherwise reused: `npm ci`/`npm install`, `pnpm install`, `yarn install` or `bun install` (from `packageManager` or the lockfile; pnpm/yarn through corepack when not installed) into `artifacts/<task>/.deps/node@<path>/`, which is linked into the run copy as `node_modules` (a hard-linked copy for Next, whose Turbopack rejects a link outside the project; npm workspaces and `file:` deps install in the run copy instead); `go mod download`; `cargo fetch`; `dotnet restore` (the `.sln` if there is one). Download caches are shared by all tasks under `sandbox.cache_dir` (default `~/.cache/xqo/toolchains`, `XQO_CACHE_DIR` overrides): npm, pnpm store, yarn, Go modules, cargo registry, NuGet. Build outputs stay per task in `.deps`: node_modules, `GOCACHE`, the cargo target dir, the dotnet CLI home. A workspace's own `node_modules`, `.next`/`.nuxt`/`.output`, cargo `target/` and dotnet `bin/`/`obj/` are not copied into runs. Telemetry is off (Next, Nuxt, dotnet, Go) and dotnet build servers are disabled so runs end cleanly. **Versions**: wanted versions come from `.nvmrc`/`.node-version`/`engines.node`, `go.mod` (`toolchain`, else `go`), `global.json` and mise's `.tool-versions`/`mise.toml`. With [mise](https://mise.jdx.dev) installed they're installed once (in mise's data dir, shared) and put first on PATH (`sandbox.versions`: `auto` (default), `mise` or `host`); without it the host's toolchains run and the result warns about a mismatch. Go fetches the toolchain `go.mod` asks for by itself, and Rust follows `rust-toolchain.toml` through rustup. The run result lists each component (`[node web: installed with npm ci]`, `[go .: reused]`, setup errors with their log), and an `npm install x` / `go get` / `cargo add` / `dotnet add package` in a command gets a note that the run's copy is thrown away, so the dependency belongs in the manifest. Settings: `sandbox.toolchains` (default `true`), `versions`, `cache_dir`, `node_modules` (`auto`, `link`, `clone`), `install_scripts` (default `true`; `false` passes `--ignore-scripts`), `components` (`[{"path": "web", "toolchain": "node"}]` instead of detection), `setup_timeout`. The local backend is **not** a security boundary: commands run as your user, with network. The xqo's own Docker image only has Python, so inside it (backend `local`) other languages need their toolchains added to that image.
- **Other languages on the Docker backend**: the same components, but each workspace runs in an image: a Node, Go, Rust or .NET project in its official image at the version it asks for (`node:<.nvmrc / engines>-bookworm`, `golang:<go.mod>-bookworm`, `rust:<rust-toolchain channel>-bookworm`, `mcr.microsoft.com/dotnet/sdk:<global.json major.minor>`; latest when unset), a Python-only one in `sandbox.image` as before. A **mixed** project (two toolchains, or Python plus one) gets a composite image built once on `buildpack-deps:bookworm` (compilers, make, python3), with each toolchain copied out of its official image and uv for Python, tagged `orch-toolchains:<hash of its Dockerfile>`; the run result says when it was built. Dependencies are installed by **setup containers** of that image, with network (`setup_network`), into `artifacts/<task>/.deps-docker/` (mounted at `/deps`) and the shared download caches (`<cache_dir>/docker`, mounted at `/cache`); node_modules is a link to `/deps/…` inside the container (a hard-linked copy for Next). Setup containers trust the host's CA bundle (`SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`/`NODE_EXTRA_CA_CERTS`, or `sandbox.ca_file`; mounted read-only) and get the host's proxies unless those point at localhost. Runs stay offline (`--network none`, plus `GOPROXY=off`, `GOTOOLCHAIN=local`, `CARGO_NET_OFFLINE=true`); the Python venv of a mixed project is built in the composite image. Settings: `sandbox.images` (`{"node": "node:20-bookworm", …}` to pick images yourself), `composite_base`, `ca_file`, plus `memory`/`cpus` (Next, Rust and .NET builds want 2–4 GB). Keep `cache_dir` and the data dir in a folder Docker Desktop shares.
- **Network on request**: runs on the Docker backend are offline. When a command really needs network (Next's `next/font/google`, Prisma engines, `playwright install`, a test against a real service), an agent calls `request_network(command, reason, grant)` and you get an attention card with **Deny / Allow this run / Allow for this task**, showing the command and the reason. Allowed: the command runs with network (the host's CA bundle and proxies, as for setup) and the result says `[network: on for this run (approved by the user)]`; "for this task" lets every later run of the task have network too (all its agents, until a restart). Denied, or **no answer before the attention timeout, is always a deny**, never an auto-approval; scheduled runs marked unattended are denied at once. Each request is logged as a `network_request` event (command, reason, answer, whether it timed out). The tool is only offered when runs are offline (Docker backend, `network` false); `sandbox.network_requests: false` (also in a department's `sandbox` block) switches it off. The local backend always has network, so it never asks.
- **Sandbox backends**: `sandbox.backend` picks `auto`, `local`, `docker` or `off`. A new backend (e.g. a remote runner) subclasses `xqo.sandbox.Backend`, sets `name` and implements `command()` (what to execute for a run copy); register it with `register_backend()` or name it as `"backend": "package.module:ClassName"`. The workspace copy, timeout, cancel and output handling are shared. An unknown backend stops startup with a clear message.
- **MCP tools**: list servers under `mcp_servers` and grant them per agent with `"mcp": ["name"]` (see `_mcp_examples` in agents.json).
  - Remote (`"url"`, optional `authorization_token` or `token_env`, `allowed_tools`): passed to the Messages API MCP connector (beta `mcp-client-2025-11-20`); Anthropic connects server-side.
  - Local (`"command"`, `"args"`, `"env"`, `allowed_tools`): launched over stdio by the xqo (needs `uv pip install ".[mcp]"`); tools appear as `mcp__<server>__<tool>`.
- **Loop protection**: no agent is asked twice in one chain, max depth 4, per-task time limit (`XQO_TASK_TIMEOUT`, default 900 s, extendable from the dashboard).
- **Resilience**: failed handovers fall through to the next offer; the SDK retries 429/5xx (`XQO_MAX_RETRIES`, default 4); prompt caching is on; per-agent token and cache usage shows in the UI. Restarts replay `logs/events.jsonl`.
- **Attachments**: add images (PNG, JPEG, GIF, WebP, up to 5 MB), PDFs (20 MB) and text files (2 MB) to a task with 📎, by dropping them on the prompt, or by pasting. A pasted screenshot becomes an image attachment, and a pasted text over 2,000 characters becomes a `.txt` attachment (click **inline** to put it in the prompt instead). Up to 20 files, 24 MB in total. They're stored in `artifacts/<task>/attachments/` and sent to the entry agent as Claude content blocks (images as `image`, PDFs and text as `document`) on the API path; Claude Code agents get their paths instead and read them with Read when needed. Agents pass them on by name with the `attachments` field of `ask_agent` / `handover_task`. Forks keep them, and the message flow shows thumbnails.
- **Git**: each task workspace is a git repo (`artifacts/<task>/workspace/.git`, branch `main`) with one commit per file version, authored by the agent that wrote it (`patch src/fib.py by reviewer (task_…)`). Agents can't touch `.git`, and it's left out of file lists, zips, the sandbox copy and downloads. Push from the dashboard (**git** button on a task's artifacts) or `POST /api/git/<task>/push`; for https remotes set a token in `XQO_GIT_TOKEN` (name configurable as `git.push_token_env`) before starting the server. It is sent as an HTTP header and never stored or logged. `"git": {"enabled": false}` or `XQO_GIT=0` turns it off; without git installed everything else still works.
- **Open task folders**: **📁** on a task's artifacts lists its task, workspace and attachment folders, each with **copy** (path to the clipboard) and **open ↗** (opens the folder in VS Code). The server only knows its own paths, so for Docker or a remote machine say how they look on your side in agents.json: `"folders": {"path_map": {"/data": "/home/me/xqo/data"}, "ssh_host": "me@devbox", "editor": "vscode"}` (env `XQO_PATH_MAP="/data=/home/me/xqo/data"` (several joined with `;`), `XQO_SSH_HOST`, `XQO_EDITOR` win). `path_map` turns server paths into host paths (the folder bound to `/data`); with `ssh_host` the links open over VS Code Remote-SSH (`vscode://vscode-remote/ssh-remote+<host>/<path>`). `editor` is `vscode`, `vscode-insiders`, `cursor`, `windsurf` or `none` (copy only). In a container without `path_map` the panel shows the container paths and a hint instead of links. Browsers can't open `file://` folders from a web page, so there is no "open in file manager"; the zip downloads stay the way to get the files themselves.
- **Replay**: **▶ replay** in the Live viewer steps through a past task from the full event log: play/pause (space), step (← →), speed, a scrubber. The graph and timeline show the state at each step.
- **Talk to a running task**: the input box has **New task | Ask | Steer** tabs and an **Urgent** toggle. Ask and Steer go to the task selected in the Live viewer (the box shows which one), to its entry agent or to the agent picked in the dropdown (or a leading `@agent`). An **Ask** is a question: the agent answers with the `reply_user` tool (a chat bubble in the timeline, Markdown/LaTeX/Mermaid rendered) and keeps its plan. A **Steer** changes the instructions ("use FastAPI instead"): it reaches every agent at work on the task, and the planner re-plans or hands off as needed. Messages wait in the agent's inbox and join its context at its next turn, so work in progress isn't broken; **Urgent** puts them first, and an urgent Ask is answered at once from a side call on the agent's current conversation. A message to an agent that is waiting on you answers that request (its auto-confirm timer stops). A message to a finished task **reopens** it: it continues in the same task and workspace with its earlier message flow as context. Everything is logged as `user_message` / `agent_reply` events, so it survives restarts, shows in replay and can be forked from. CLI: `xqo ask|steer <task> "text" [--to agent] [--urgent]`. `@engineering` (or the department in the picker) sends it to that department's head, and a Steer to everyone also reaches the heads at work.
- **Pause and resume**: **⏸ pause** in the Live viewer, or **Urgent** on a New task, which pauses the selected running task and starts the new one at once (other running tasks are untouched; non-urgent tasks simply run alongside). Model calls in progress finish, then the task's agents wait; test runs are stopped and auto-confirm timers freeze; time on hold doesn't count against the task's time limit. **▶ resume** (Live viewer or ☰ tasks) releases it, and its agents get a short note plus any Steer messages sent meanwhile. Resume on a task that is no longer running (finished, or paused when the server stopped) continues it like a reopen. `task_paused` / `task_resumed` events; `paused` status and badge on the graph. CLI: `xqo pause|resume <task>`.
- **Test results**: every `run_code` is marked `[PASSED]` or `[FAILED: exit N]` for the agent, with instructions to fix and re-run. After 3 failed runs in a row the user is flagged (**tests keep failing**: keep fixing / stop / guidance; auto-confirms *stop*). A sub-task whose last run failed returns its result with a note saying so, so the planner can't miss it; runs, failures and the last exit code are kept on each task (`tests` in the task tree, a **tests failing** / **tests pass** badge in the Live viewer).
- **Cancel**: **⏹ cancel** in the Live viewer (or **☰ tasks**), `POST /api/tasks/<task>/cancel {reason?}`, or `xqo cancel <task>` stops a running task: in-flight model calls are dropped, open questions to you are closed (`cancelled`), and sandbox runs are killed with their child processes (Docker containers too). Status becomes `cancelled`; files made so far are kept and a final commit `Task cancelled by …` records the workspace. `task_cancel_requested` and `task_cancelled` events say who cancelled and why. A cancelled task can still be replayed and forked. It stops the work in every department, ends pending cross-department handovers, and keeps the usage counted up to that point.
- **Delete**: finished tasks (done, error, cancelled, interrupted) can be deleted; a running one must be cancelled first. **🗑 delete** in the Live viewer, or **☰ tasks** to select several. Deleting moves the task to `artifacts/.trash/<task>/` and hides it everywhere, with **Undo** (or **Trash → Restore**, `xqo restore <task>`). It is removed for good after `"trash": {"retention_days": 7}` (`XQO_TRASH_DAYS`; `0` keeps it until you purge), or at once with **Delete permanently** / `--permanent`: the task's folders (workspace and git repo, history, notes, attachments, venv), its manifest rows and its events in the log go; a `task_deleted` record stays. Tasks branched from it are kept and only lose their link back (the confirmation lists them). The task's department workspaces (`artifacts/<task>.<dept>/`), notes boards and published files go with it. `xqo delete` / `restore` talk to the server at `--url` (`XQO_URL`), or work on the data dir when no server runs.
- **Archive**: **🗄 archive** in the Live viewer (or select several in **☰ tasks**) hides a finished task from the task list, the message flow and the artifacts panel. Nothing is removed and it never expires: workspace, git repo, history, notes, replay and fork all stay. **☰ tasks → 🗄 Archived** lists them with **Unarchive**; asking, steering or resuming an archived task (dashboard or CLI) brings it back first. Only finished tasks (done, error, cancelled, interrupted) can be archived. An archived task can still be deleted, and restoring it from the trash brings it back archived. The archived ids and the trash index are kept in one file, `artifacts/lifecycle.json` (lifecycle.py); `task_archived` / `task_unarchived` events record who did it. CLI: `xqo archive|unarchive <task>…` (through the server, or on the data dir when none runs).
- **Scheduled and repeating tasks**: **⏱ schedules** in the Live viewer. A schedule starts an ordinary task (same path as **Submit**) on a timetable: **once** at a date and time, **every** N minutes / hours / days, **daily / weekdays** at given times, or any 5-field **cron** expression, in a time zone of your choice. Each run is named `<schedule> #<n>`, shows **⏱** in the task list and a badge in the Live viewer, and can be replayed, forked, archived or deleted like any task. Upcoming runs stay in the Schedules panel: next and last run, run count, **▶ Run now**, **Edit**, **History** (started / skipped / missed / finished runs with links to their tasks), pause / resume and **Delete** (tasks already started are kept). Per schedule:
  - **Overlap**: if the previous run is still running, paused or waiting on you, the new one is *skipped* (default, logged), *queued* (one run starts when the previous one ends) or run *in parallel*.
  - **Missed runs** (server down): *run once* at start-up if no older than the grace (default 1 h), or *skip*. Missed runs never pile up.
  - **Limits**: max turns and max output tokens for that run's task tree, and a **max cost per run** that cancels the run when its estimated cost reaches it (Claude Agent SDK sessions report their cost when they end, so a run on the SDK path is stopped after the session that crossed the cap). The **No limits** hour does not apply to scheduled runs unless you tick it for the schedule. hq department budgets stay in force.
  - **Unattended** (default): questions to you (ask_user, budget, time limit, …) take their default answer at once instead of waiting for the attention timeout (`auto_confirmed` by `unattended`). Untick it to have runs wait like any task.
  - **Failures**: after 3 failed runs in a row (error, cost cap, cancelled by anyone but you; configurable, 0 = never) the schedule pauses itself and the dashboard shows a notice. **Stop after** N runs or a date; **archive finished runs after** e.g. `7d`.
  - Schedules made in the dashboard, API or CLI live in `artifacts/schedules.json` with their run state and survive restarts; attachments are copied into every run. `"schedules": [...]` in `agents.json` adds schedules kept with the config (🔒 in the panel: pause, resume and run there, edit in the file):
    ```json
    "schedules": [{"name": "Daily report", "agent": "planner", "prompt": "Summarize yesterday's work",
                   "cron": "0 7 * * 1-5", "tz": "Europe/Berlin", "limits": {"max_cost_usd": 2}, "archive_after": "14d"}]
    ```
    Keys: `name`, `prompt`, one of `cron` / `every` (`"6h"`) / `at` (`"2026-11-01T09:00"`) or a `trigger` object, and optionally `id`, `agent`, `tz`, `enabled`, `overlap` (`skip` / `queue` / `parallel`), `missed` (`run_once` / `skip`), `grace`, `limits` (`max_turns`, `max_tokens`, `max_cost_usd`, `honor_no_limits`), `unattended`, `max_failures`, `end` (`after_runs`, `until`), `archive_after`.
  - Only the `serve` process runs schedules, and only one process per data dir (it holds `artifacts/scheduler.lock`; a second one says so and does not run them). In Docker, schedules are kept on the `/data` volume. Each HQ runs its own schedules; the office relay can read `schedules` of the HQs it lists. An external cron or systemd timer calling `POST /api/tasks` still works if you prefer it.
- **Fork**: **⑂ fork** on any event (or **fork here** during replay) starts a new task branched right after that event, with an editable prompt and entry agent. The fork gets the workspace files and notes board as they were at that point (one `fork` commit) and the earlier message flow as context (capped at 20k chars). The original task is untouched, and the tree shows "forked from…".
- **Artifacts**: every fenced block in any agent reply is saved with a UTC timestamp and indexed in `artifacts/manifest.jsonl`.
  - **Named files** keep their folder structure in a shared per-task workspace: `artifacts/<task>/workspace/<path>` (latest), with every version kept at `artifacts/<task>/<agent>/<sub_task>/<ts>/<path>`. Unnamed blocks are saved as `<ts>_<n>.<ext>`.
  - **File-name formats recognised** (see `xqo/fences.py`): ```` ```python src/app.py ````, ```` ```src/app.py ````, ```` ```python:src/app.py ````, `title=` / `file=` / `filename=` / `path=` attributes, pandoc ```` ```{.python file="x"} ````, `(path)` / `[path]`, a line before the fence (`**path**`, `` `path` ``, `### path`, `File: path`, `path:`, "Create `path` with…"), or a first-line comment (`# file: path`, `// filename: path`, `<!-- path: x -->`, `/* file: x */`, `-- file: x`, bare `# src/app.py`). Paths are sanitised.
  - **Patching**: ```` ```diff ```` unified diffs (multi-file, new/deleted/renamed files: a rename diff removes the old path, tolerant of wrong line numbers; all-or-nothing), SEARCH/REPLACE blocks, or `patch_file`. Failures go back to the model (2 retries), then to you.

Switch with **3D / 2D** in the header (remembered per browser, or `?view=2d`); without WebGL the page falls back to 2D by itself. Nothing is loaded from the internet and no Node server is needed. Each department gets its own area with a desk per agent (★ marks the head). Agents follow the live event stream: they sit and type while they work, walk over to the agent they message or hand work to (with a speech bubble), sleep on a beanbag while their task is paused, and when idle act out small routines (see *Idle routines* below) or wander the lounge, and wear a red **!** while a request waits for you. While they work, code scrolls on their screen (at a pace that changes now and then, with the odd flicker; red while they wait for you). A new task gets an instant "Got it" from its agent, which hurries to its desk; when a task you gave finishes, its agent nods (or shakes its head) and keeps a green ✓ (red ✗) until you click it. Speech bubbles wrap over up to 4 lines and stay at least 5 seconds. The header shows the overall tokens and estimated cost of this HQ in the middle (of every HQ in the planners world), and the HQ name (`"name"` in agents.json) instead of "HQ". In 3D, name tags have their department's colour, a double-click on an agent makes the camera follow it (Esc or a pan stops it), and the windows turn a lighter or darker grey-blue with your local time of day.
- **Click an agent** for a side panel: its requests waiting for you (option buttons or a typed answer), its tasks, **Ask** / **Steer** / **pause** / **resume** on the selected task, **open in dashboard ↗**, and **New task** for that agent. Everything goes through the dashboard API; the office itself never receives commands.
- **Click an agent's monitor** (or its desk, also a desk without a computer, or its chair) for the same panel; an agent that is away from its desk (idle, at a routine, or resting while paused) hurries back to its seat and stays there while the panel is open, at most a minute. This is only the office's picture: nothing is sent to the agent.
- **Task picker** in the header: show only the agents working on one task (the others step out).
- **✎ edit** (3D, only when the server runs with `serve --edit` or `"office": {"edit": true}`; without it the button is hidden and the server refuses every layout and model change): change the office in place. Switching to 2D leaves Edit mode; switching back to 3D does not start it. The agents step out; drag furniture to move it (Shift: half tiles), **R** turns it, **Delete** removes it (an automatic one is hidden), **Paths** shows where agents walk and paints no-go and corridor tiles (waypoints set where idle agents wander), arrows nudge, **Ctrl+Z / Ctrl+Y** undo and redo, **Ctrl+D** duplicates, **Ctrl+S** saves. The side panel adds furniture from the catalog (desks, meeting table, sofa, partition walls, plants, lamps, server racks…), sizes each room, picks each agent's character and who sits at a desk, sets the colours, uploads your own `.glb` models and characters, and exports / imports the layout file. What you change is kept per HQ in `<data dir>/artifacts/office.json` (models in `artifacts/office-assets/`) and laid over the automatic office, so new agents and departments still get a desk and a room. Another HQ's office shows its own layout but is edited on its own dashboard. Details: [Editing the office](#editing-the-office); screenshot: [`dashboard-office-edit.png`](img/dashboard-office-edit.png).
- **🤝 planners** (`/office?world=planners`): the planners of this HQ and of the other HQs listed in `"office"` in agents.json, in one room, named `<name>/<agent>`. The side panel works there too; it reaches another HQ through this dashboard's office relay, which only forwards the calls the office makes (read agents, tasks, requests and live events; submit a task; Ask / Steer / pause / resume; answer a request) and only to the listed dashboards. Click a name tag to open that HQ's office.

```json
"office": {
  "name": "hq-a",
  "planners": ["planner"],
  "hqs": [{"name": "hq-b", "url": "http://127.0.0.1:8002", "link": "http://127.0.0.1:8002"}]
}
```
`"edit": true` allows office editing without the `--edit` flag (either one is enough; default false). `name` defaults to `hq`, `planners` to agents named `planner` or with the `planning` skill in headquarters. `hqs` lists the other dashboards: `url` is where this server reaches them, `link` (optional) where your browser opens them. `XQO_OFFICE_HQS="name=url;name=url"` overrides the list. The relay has no login of its own, like the dashboard: keep dashboards on `127.0.0.1` and reach other machines over an SSH tunnel or a private network.

### Idle routines

Idle agents (only those with no work) at random walk to a spot and pretend for 6-30 s: **read** at a bookshelf, **drink** at the coffee bar or fridge, **sit** on the sofa, **write** at a whiteboard, **tend** a plant, or **chat** in a group of 2-4 around a sofa, bar or bookshelf. A spot is never shared; the stay starts on arrival (an agent that cannot get there gives up after 2 minutes); an agent that gets work drops the routine at once. 3D plays real poses (sit, hold, interact, nod). 2D plays the character sheets (`*_idle.png`, `*_stand.png`) and a small icon (📖 ☕ 🛋 ✎ 💧 💬); At a spot an agent looks at its prop (or at its chat group): sideways uses `idle_left` / `idle_right`, up or down the act's own sprite; chat uses `talking` and alternates with the side sprite. To replace them, repaint `office/citizens/<name>_idle.png` (rows: read, drink, tend, write; 4 frames) and `<name>_stand.png` (rows: idle_left, idle_right, sit_down, sit_up; 2 frames), 64 px frames, same grid; `tools/make_placeholder_sprites.py` generates throw-away placeholders (it overwrites these sheets: do not run it). It is on by default:

```json
"office": {"idle": false}                                   // off: agents only wander
"office": {"idle": {"activities": ["read", "drink"], "chat": false, "max_away": 0.4}}
```
`activities` is any of `read drink sit write tend` (default all); `chat` allows groups (default true); `max_away` (0-1, default 0.6) is the share of agents allowed away from their desks at once. Spots come from catalog anchors with an `"act"` field (`read|drink|sit|write|tend`, plus a `type` of `work|rest|social|utility|wander`), so your own catalog props and `.glb` models can offer routines too. The automatic lounge now includes a sofa. `/api/office` returns the resolved `idle` settings.

### Editing the office

The office is laid out automatically: a room per department (a desk per agent, a whiteboard, a plant and a bookshelf), windows on the back wall and a lounge along the bottom. **✎ edit** in the 3D view changes it, when the server was started with `--edit` (`xqo serve --edit`; in Docker add `--edit` to the command in docker-compose.yml). Without it the office can be looked at but not changed: the button is hidden and the server answers 403 to every layout or model change; what you change is saved for this HQ in `<data dir>/artifacts/office.json` and laid over the automatic layout, so when agents or departments are added they still get their desk and room, and your changes stay. In Docker that is on the `/data` volume, so it survives rebuilds. **automatic office** in the editor (then Save) goes back to the automatic layout; so does deleting the file.

- **Moving, turning, hiding**: automatic props are known by a stable name (`desk:<agent>`, `board:<department>`, `plant:<department>`, `shelf:<department>`, `window:<n>`, `coffee_bar`, `rug`, `beanbag_l`…); a desk takes its chair along and its agent sits facing it however it is turned. Positions count from the top-left of the prop's room (or of the lounge, or of the building), so a room keeps its furniture when the automatic layout moves it.
- **Adding**: the catalog is `xqo/plugins/office/static/office3d/catalog.json` (Kenney models and built-in shapes). An added prop belongs to the room it is dropped in. A prop with a *work* spot (a desk) can be given to an agent ("Who sits here"); *rest*, *social* and *utility* spots (beanbags, sofas, tables, the coffee machine) are where idle and paused agents go.
- **Paths**: in Edit mode the floor shows where agents can walk (red: blocked by furniture or the wall, green: corridor, coloured squares: the spots agents use, magenta: spots they cannot reach). **no-go** and **corridor** in the Paths section paint tiles by dragging over the floor (**erase paint** removes it, Esc goes back to moving furniture): agents never step on a no-go tile and prefer corridors. Paint is kept per room, like props. Idle agents wander between **waypoints** (`wander:lounge`, `wander:hall`…, and any you add from *Add › paths*); they show only while editing. Partition walls block, a **doorway** does not. The panel warns when an agent's desk (or another spot) cannot be reached. Agents head for different tiles, walk around agents who stand in their way and step aside for those walking past. In 2D, no-go paint and waypoints apply; corridors are 3D only.
- **Your own models**: upload a binary glTF (`.glb`) in the editor: [Kenney](https://kenney.nl/assets) kits (CC0, same style), [Blockbench](https://www.blockbench.net) for low-poly props and characters, or [Blender](https://www.blender.org) (File → Export → glTF 2.0, format *glTF Binary*). Give its footprint in tiles; without a `scale` it is fitted to that footprint. Uploaded files are kept in `artifacts/office-assets/` (up to 20 MB each, 200 files) and listed in `office.json`'s own `catalog`. Characters with Kenney's animation names (`idle`, `walk`, `sit`, `emote-yes`) move like the others; a model without them stands still.
- **Sharing**: **export** downloads `office.json`; **import** loads one (checked first, then Save). Uploaded models are not inside that file: upload them on the other HQ too (they show as pink boxes until then).
- **Two editors**: saving checks that nobody saved in between (another tab or person); if someone did, Discard loads theirs. Pages that only watch the office pick up a save within about 10 seconds.
- **By hand**: `office.json` can also be written by hand or by a script; the format is described in `validate_layout` in `xqo/plugins/office/view.py`. A file with a mistake is ignored (the office opens automatic and the editor says why).
- **Security**: like everything on the dashboard, editing the office and uploading models needs no login, so keep the dashboard on `127.0.0.1`. Uploads are checked to be `.glb` / PNG / JPEG files and are served with `nosniff` and a sandbox policy. The office relay never forwards edits to another HQ.

```json
{"version": 1,
 "rooms": {"engineering": {"size": [14, 10]}},
 "props": {"desk:coder": {"x": 6, "y": 2, "rot": 90}, "plant:hq": {"hide": true}},
 "added": [{"uid": "u-1", "type": "sofa", "zone": "@lounge", "x": 10, "y": 3, "rot": 0}],
 "agents": {"coder": {"character": "character-male-c"}},
 "paint": {"engineering": {"block": [[0, 5], [1, 5]], "path": [[4, 6], [5, 6]]}},
 "theme": {"floor": "#b9bec6"}}
```
